# CLAUDE.md — SSBM Stats

## What this is

A zero-backend web app: a Melee player points their browser at their local Slippi replay folder and gets a stats dashboard. All parsing happens client-side via `@slippi/slippi-js` in web workers. The privacy contract, precisely:

1. **Raw `.slp` files never leave the machine — hard product constraint, no exceptions.**
2. Parsed `GameRecord` stats (~5 KB/game — ~1 KB of headline stats plus the per-move table) may sync, but only **opt-in**, only to **the Supabase project that deployment is configured against** — the user's own when self-hosted, the operator's on ssbmstats.com — behind `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` env vars, with per-user row-level security. Without those vars `supabase` is `null`, `CloudSync` renders nothing, and the app is exactly the local-only tool described here. Never tell a hosted user their stats sync to "their own Supabase": on ssbmstats.com those rows sit in the operator's project, isolated per user by RLS. "Your private account" is the honest claim; the stronger one is a privacy misstatement.
3. No telemetry, analytics, or any other non-opt-in transmission of **replay-derived** data — ever. Aggregate visit counting is the one exception, and it never touches replay data: the hosted ssbmstats.com mounts Vercel Web Analytics (`<Analytics />` in `main.tsx`), which is cookieless, identifies no one, and reports page views, referrers, and country only. It loads `/_vercel/insights/script.js`, which exists solely on Vercel, so a self-hosted build carries the mount inertly and transmits nothing.

## Architecture

```
folder pick ─► discovery (*.slp) ─► dedup vs IndexedDB ─► worker pool (slippi-js)
                                                              │ GameRecord (~5 KB)
              React dashboard ◄── memoized selectors ◄── IndexedDB (Dexie)
                                                              │ opt-in, stats only
                                                        Supabase (configured project)
```

- `src/lib/pool.ts` — file discovery (FS Access API + `webkitdirectory` fallback), worker pool sized to `hardwareConcurrency` on measured 4/6/8 tiers and capped at 8. The final bounded parser measured 44.7/52.5/54.8 games/s over two 240-game rounds, so 8 is evidence-based rather than the old 10–16-worker guess that could lose throughput to memory pressure. The queue is sorted **newest-first**, so the games streaming into the dashboard first are the recent ones rather than whatever order the directory walk happened to use. Workers are handed the `File` **unread**: structured-cloning shares its blob rather than copying bytes. The re-stat that guards reads stays on the main thread because it needs the cache's id set. Medium imports run the header preview described below; memory-safe imports (5k+ pending files) skip it, stay at three workers, stream only progress, and install the completed IndexedDB cache once. DB flushes are one 250-record storage pack per transaction on a promise chain; storage failures surface as `RecordSaveError` after the run, never as silent loss. UI delivery is time-throttled (~1 s for records, 250 ms for progress counts) because every record append invalidates App's O(n log n) resolve+sort. An `AbortSignal` (App's reset) stops feeding, flushing, and callbacks; parsed-but-unflushed work is dropped by design.
- `src/worker/parser.worker.ts` + `src/lib/parse.ts` — one replay → one `GameRecord`. Stats-only: frame data is computed over then discarded. Corrupt files get tombstone records (`parseError` set) so they're never re-parsed. `parseHeaderFile` reads the settings prefix, fixed GAME_END command and metadata tail as separate `File.slice()` ranges; it does not read the multi-megabyte frame body that the full pass will read moments later. `parseReplay` runs slippi-js's existing computers in 2,048-finalized-frame batches and releases completed batches from both internal frame maps, then folds per-aerial L-cancels and teams stats through the same frames before release. `parseReplayRetainedForVerification` keeps the old retained-frame path only as a parity oracle. Both header paths resolve win/loss through the single `decideWinner` helper. `dropUnreadComputers` narrows slippi-js's six registered stat computers to the three whose output is actually read (actions, conversions, inputs) — combos, stocks and target breaks were being computed over every frame and discarded, ~10% of a full parse. It reaches into TS-private fields, so it is guarded: an upgrade that changes the shape leaves every computer registered and the parse merely slow. **If a future stat needs combos or stocks, re-register the computer there.** Teams input counting guards a frame whose predecessor is missing a player: the library does not check that lookup, and one such frame used to tombstone the whole game. Only the input sample is skipped now, never the game.
- `src/lib/db.ts` — Dexie/IndexedDB. Cache key is `path|size|mtime` — that is a *file* key, answering "have I parsed this file?"; game identity is separate (see `dedupe.ts` and decision 8). `kv["myAccounts"]` holds the user's `Account[]`, with a read-fallback to the pre-multi-account `kv["myCodes"]` string array — that fallback is the local migration path and must outlive the cloud one, since no backfill ever ran against anyone's IndexedDB; drop it and an existing user lands back on the identity prompt with a full cache. Records live packed ~250/row (`packs`) with an id-only `seen` table for dedup — per-row IndexedDB overhead made 30k-game restores slow. Browser-local; optionally mirrored to the Supabase project configured for that deployment. Also stores the picked `FileSystemDirectoryHandle` in `kv` so a return visit can re-walk the folder without re-prompting: the app auto-rescans on load when the permission is still granted, and the topbar **Refresh** button re-requests it (needed after a browser restart) — both dedup against the cache, so only new replays parse. **Change folder** is the full reset (`clearAll` + abort + generation bump).
- `src/lib/stats.ts` — identity inference + all aggregation selectors. Pure functions over `ResolvedGame[]`.
- `src/lib/dedupe.ts` — `gameKey(rec)`, a content-derived identity (`playedAt|stageId|sorted player sides`) that survives the replay folder being copied, moved, or synced through a service that rewrites mtimes, plus `dedupeRecords()`. See decision 8.
- `src/lib/model.ts` + `src/worker/model.worker.ts` — logistic-regression win model (IRLS, O(iterations·n·k²)) fitted in a worker with plain-data in/out; `null` model means "not enough data". `src/lib/coach.ts` — z-score- and sample-size-gated recommendations. Both feed the Insights view, which caches fits by games-array identity so tab revisits don't refit.
- `src/lib/supabase.ts` / `src/lib/cloudSync.ts` / `src/components/CloudSync.tsx` / `supabase/schema.sql` — optional cloud sync. Records are content-keyed by `gameKey()` inside 256 deterministic JSONB buckets per user (`game_record_packs`), with a compact key→stats-version object beside each records object. This is a storage constraint, not cosmetic: the old `game_records` table reached ~767 MB at 264k rows plus ~131 MB of indexes; packed values let PostgreSQL compress the repeated GameRecord shape and pay row/index overhead once per bucket. Browser and SQL use the same FNV-1a low-byte bucket, and all writes go through the version-aware `merge_game_record_entries` RPC under per-user/bucket advisory locks so two devices cannot erase each other's additions. Full restore pages pack data; normal sync persists a content-key set and pulls only pack metadata newer than its `updated_at` cursor. `pack-migration.sql` copies the legacy table non-destructively; `pack-cleanup.sql` takes an exclusive lock, captures late old-client writes, verifies every key, then truncates the legacy copy. **Only games one of the user's own accounts played are pushed** (`isSyncable`): a shared replay folder holds housemates' games too, and those are cached locally — identity is query-time, so adding an account later has to be able to claim them — but uploading someone else's stats isn't the user's call. The same predicate must gate CloudSync's `pending` count, or foreign games stay unsynced forever and pin the button gold. Pull stays unfiltered because RLS already scopes it and fresh-device restore runs before identity is known. `user_codes` (one row per account, with `label` and `sort_order`) is the identity store. Sync is automatic — on sign-in, ~2.5 s after newly parsed games stop streaming in, and on tab re-focus (≥15 minutes apart) — so devices converge without user action; the gold button is the manual fallback after failure. One auto-push attempt per pending count: failures must not retry-loop.
- `src/lib/demo.ts` — deterministic synthetic data (seeded PRNG); keep it deterministic.
- `scripts/lib/gif-encode.mjs` + `scripts/lib/gif-draw.mjs` — the shareable-animation pipeline: a from-scratch GIF89a encoder (LZW, one global popularity palette) and the frame painters. **Plain JS with `.d.mts` siblings on purpose** — the identical modules are imported by the browser (the Share GIF buttons, via dynamic import so they stay out of the tab's chunk) and by Node (`scripts/render-liquipedia-assets.mjs`, headless via `@napi-rs/canvas`), and Node can't load `.ts`. Fonts are generic stacks because CI has neither Chakra Petch nor IBM Plex Mono. Generated assets land in `public/share/` (gitignored) and are **rendered during the Vercel deploy** via `npm run build:deploy`, never committed — a re-rendered GIF is ~2.5 MB of binary that can't delta-compress, so committing them on each data change would grow the repo without bound. A failed render must not fail the deploy, hence the `|| echo` in that script. They're also excluded from the PWA precache (`globIgnores`): a multi-megabyte GIF has no business in the offline bundle. Both paths sample the race through the same `sampleFrameIndices` helper — which always keeps the final frame, since that's the one the loop holds on — so an exported GIF and a served one contain the same frames.
- `src/lib/liquipedia/` + `src/components/liquipedia/` + `scripts/refresh-liquipedia.mjs` — the **Liquipedia tab**: scene-wide Melee history (majors, SSBMRank editions, career winnings), the one view that shows nothing about the user's own replays. `data.ts` is a **generated bundled snapshot**, not a runtime fetch: the app has no backend and the CSP allows self + Supabase only, so the dataset ships in the (lazy) chunk and works offline. A weekly GitHub Action (`.github/workflows/liquipedia-refresh.yml`) runs the refresh script and commits `data.ts` alone; share images are a deploy-time artifact, not a tracked one. The refresh is **append-only** — it adds majors and ranking editions not already present (deduped on name+year, never on date, or an event listed late would be invisible forever) and never rewrites existing rows, so a parser miss costs an update rather than the dataset. It bails loudly if more than 25 majors look new, since that means the parser drifted rather than that history changed. It exits 2 when Liquipedia rate-limits it, which the workflow treats as "nothing to do". The one thing it revisits is a player whose winnings are still unknown. Because append-only means a parser fix can't reach existing rows, `scripts/rebuild-liquipedia.mjs` re-derives everything from the source pages; it stays manual since a `--force` run is two requests per champion 30 s apart (~30 min today); without `--force` it reuses known winnings and fetches only the two index pages. Fetching, and reading/writing `data.ts`, live in `scripts/lib/liquipedia-fetch.mjs` and `liquipedia-data.mjs` so both paths share one definition.
  - **The figures live in rendered HTML, not wikitext.** Majors parse from `prop=text` (the `divRow`/`tournament-card-premier` markup, where the premier class is the only supermajor signal — miss it and the count reads ~30% low), rankings from `prop=wikitext` (`{{PRplayer}}`, where `{{!}}` is an escaped pipe that will truncate a name if you match templates naively), and career winnings only from the rendered player page. Two parsers were written against the wrong source before this was understood; `scripts/inspect-liquipedia-page.mjs` plus the **Inspect Liquipedia page** workflow exist to print the real markup rather than guess, and to do it from a runner, because Liquipedia blocks a developer IP for hours after any burst.
- `scripts/build-nikki-public-archive.mjs` + `scripts/load-public-archive.mjs` + `src/lib/publicArchive.ts` + `supabase/public-archive.sql` — the **public replay archive**. Raw `.slp` files never enter Supabase: the local pipeline deduplicates, curates, and emits derived game/player rows plus display rollups, excluding source paths, filenames, unresolved tags, connect codes, and private user IDs. Archive tables are separate from private user-sync and `community_user_rollups` tables. Published dataset revisions are immutable; clients select the latest published revision by `data_as_of` then `published_at`. The current `nikki-2026-09-02-v7` revision contains 160,075 unique games, 152,566 broad usable games, 25,598 conservative tournament games, and 27 published evidence-backed player identities. The broad games represent 321,668 player-games because singles have two sides and doubles four—never label that number as distinct games.
  - **Community comparisons stay separate.** “SSBM Stats” is the opt-in, privacy-thresholded user cohort; “Venue archive” is the broad public-event sample; “Tournament archive” is the verified/probable set sample; “Pro tournament archive” aggregates only externally resolved Top 100 identities. Matchup, Stage, Move, headline execution, and Execution-chart references use those same definitions. Move-difference highlighting compares the user's value with Tournament when present and Venue otherwise. Execution reference lines are fixed horizontal aggregates, never implied archive time series. Missing SSBM Stats character rows render as unpublished/dashes, never zero; likewise the all-opponents Stage view must not sum privacy-suppressed matchup cells and leaves SSBM Stats blank until a true character-by-stage aggregate exists. The public threshold remains 25 contributors and 100 player-games even though the UI is not feature-gated.
  - **Named identity is conservative and pro-first.** The current directory contains 27 published evidence-backed players; ambiguous tags remain anonymous in aggregates. Pro controls list every published player with their primary archive character. In the Public Replay Archive, selecting a pro switches to Event mode, restricts the Event menu to that player's mapped events, chooses the first event alphabetically, and selects the player's most-observed character at that event. Manual character filtering may select another mapped character; it must not expose an identity without evidence.
- `scripts/forecast.mjs` + `scripts/lib/forecast/` + `src/components/TournamentPredictions.tsx` — the **Tournament Predictions** research and public-derivative pipeline. The ignored `.forecast/` workspace holds raw Start.gg responses, the 84-event canonical dataset, nested tuning checkpoints, reports, and upcoming-event snapshots; `.env.forecast.local` holds the token. Neither is committed. Tracked mappings, corpus contracts, tests, builders, and sanitized generated bundles let a clean clone reproduce the current website without those local files. Release 0.4.6 exposes six model families, an 83-event/74,891-set chronological comparison, strict-history and separately labeled seed-sensitivity modes, and the deterministic Riptide 2026 Top-16/Top-8 seed scenario. Coverage means both players had the model's required prior inputs; it is not accuracy. The results are retrospective rather than snapshot-verified title-odds evidence, no model family is selected, future-event refresh is manual, and the automatic feed stays last. Keep [the roadmap](docs/predictions-todo.md), [methodology](docs/forecast-research.md), and [handoff guide](docs/forecast-handoff.md) synchronized with generated bundle counts and hashes.
- `scripts/render-seo-pages.mjs` + `scripts/lib/metrics-data.mjs` — the static pages a crawler can read. The app is client-rendered with no router, so the HTML Vercel serves is an empty `#root` and there was nothing to index. This renders `/about`, `/metrics` and `/melee-majors` as real HTML into `dist/` after `vite build`, plus the `sitemap.xml` listing them. **Generated, never hand-written**: the metric definitions come from `metrics-data.mjs` — the same module `MetricsGuide.tsx` renders, plain `.mjs` with a `.d.mts` sibling for the same Node-cannot-load-`.ts` reason as gif-draw — and the majors table from the bundled Liquipedia snapshot, filtered to offline events per decision 6. Neither can drift from what the app shows. Output goes to `dist/` rather than `public/` deliberately: `public/` would enrol them in the PWA precache, and they are documents for crawlers, not part of the offline shell.
- `src/components/` — Overview (+ ShareCard PNG export), Teams, Sessions, Insights, Records, MetricsGuide, CloudSync, FilterBar, Landing, Community, TournamentArchive, TournamentPredictions, and Views.tsx (Matchups, Stages, Opponents, Execution, GameLog), plus the identity/chrome pieces: AccountsEditor (the multi-account editor from decision 1), AccountFields, ProgressAndIdentity, Kpi, GoogleG. Community's Atlas consolidates matchup, stage, and move comparisons; the headline table compares the selected local character against SSBM Stats, venue, tournament, aggregate pro, and optional named-pro samples. Views are lazy chunks — which is why the PWA precache must cover everything. `src/main.tsx` is the entry point and owns service-worker registration (see Deployment).

## Key decisions (do not silently reverse)

1. **Players are stored neutrally** in `GameRecord.players[]` with `winnerIndex` (singles) / `winnerTeamId` (teams), NOT as self/opponent. Identity (the user's connect code(s)) is chosen after parsing and applied at query time (`resolveGames` / `resolveTeamGames`). This makes alt accounts and identity changes free. Never bake "self" into the stored record.
   - **The user has an `Account[]`, not a code.** One person routinely owns a main and an alt whose replays land in the same folder; every account is "you", games are pooled across all of them, and `Filters.accountCode` splits them back apart. Labels ("Main", "Alt") are display only — resolution matches on `code`. They render as `Main (ABCD#123)` in dropdowns via `accountLabel()`, and as the bare label in dense tables via `codeShort()`. Because identity is query-time, the Accounts editor changes it with a recompute and **never a re-parse or a cache clear** — do not route account edits through the "Change folder" reset.
   - **Two of the user's own accounts in one game** (`selfMatch`) carry no result: `isWin` is forced null, which excludes them from every win-rate denominator for free, and they are skipped in `byOpponent`, `byTeammate`, `byTeammateDamage` and the card's rival. They stay visible in the game log, badged "self". Rare in practice — it needs a lent account — but the alternative is crediting a coin-flip win to whichever port sorted first.
   - **Singles vs teams is an axis separate from `gameType`** — a 2v2 is still ranked/direct/offline. `Filters.format` switches the dashboard between the singles tab set and the single consolidated `Teams` view; the two never mix in one aggregation. Teams selectors resolve me/teammate/opps and win/loss at the team level. `resolveTeamGames` skips anything that isn't a clean 4-player two-team game rather than guessing a teammate.
2. **Win/loss ladder**: gameEnd placements → stock-out survivor → LRAS initiator loses. Games under 30 seconds are `winnerIndex: null` (indeterminate) and excluded from win-rate denominators but still shown in the game log. It lives in exactly one function, `decideWinner` in `parse.ts`, because both parse passes run it. The stock-out branches guard on `stocksRemaining !== null`, and the header pass — which cannot see the final frame — relies on that: it makes the header verdict a **strict subset** of the full one, able to leave a result undetermined but never to name a different winner. Keep that property. It is what lets the preview's win rates stand on screen without being corrected out from under the user, and a stock-out branch that stopped guarding on null would break it by crediting the win to whoever sorted first.
3. **Frames are discarded.** Custom frame-level metrics (wavedash quality, ledgedashes) are a future feature behind an explicit opt-in re-parse — don't retain frames to make a feature easier.
   - When a new per-game stat is added, bump the Dexie version and invalidate stale `packs` + `seen` rows (see v9–v11/v13 for full clears and v14 for a surgical migration; `games` is a legacy empty store since v8). `GameRecord.statsVersion` is the lightweight cloud payload marker: stale cloud rows may remain visible while a remembered folder reparses them, but they must never enter `seen` or overwrite a current row.
   - Optional classification metadata is the narrow exception: it may be added without a version bump only when absence means "unknown" and unknown records remain fully eligible everywhere. CPU status follows this rule. A game is excluded only when a participating player has `isCpu === true`; `false`, `undefined`, and conflicted `null` never exclude it. Never clear caches or require a replay refresh merely to classify old games.
   - The header pass of decision 10 is not an exception to that rule, and must not be turned into one: its records are **never written to IndexedDB and never pushed to the cloud**, so no mixed-schema row is ever stored anywhere. Cache them and the rule really does break — a half-parsed library would persist across reloads with no way to tell which rows were which.
4. **The "By mode" panel on Overview ignores the mode filter** (applies all other filters) so overall/ranked/unranked/direct rows are always all visible for comparison. Preserve this when refactoring filters.
5. **Only tournament-legal stages count** — `INCLUDED_STAGE_IDS` in `src/lib/config.ts`; games on other stages are dropped at resolve time and never reach any view.
   - **And only the 26 playable characters** — `INCLUDED_CHARACTER_IDS`, same file, same treatment at the same place. Melee's external character table runs on past the roster into Master Hand, the wireframes, Giga Bowser, Sandbag and Popo (IDs 26–32); none is selectable in a versus match, but replays reporting one do reach real users, and they surfaced as an unnamable "Char 31" row in the matchup tables. A game is dropped **whole if either side is outside the list**, not just hidden from the character views: there is no honest name for the row and no way to tell what was actually played, so the half we could report isn't trustworthy either. `charName()` names 26–32 anyway, as a backstop for any path that doesn't resolve through `resolveGames`. `fetchCommunitySnapshot` filters the same way, because that aggregate is computed server-side over every synced game — including ones pushed by clients built before this existed.
6. **The Liquipedia tab is bundled, cited, and append-only.** It is public scene history, so it deliberately ignores the global `Filters` (a note in the view says so) and never touches replay data — which is also why it's reachable straight from the landing page (`browsingHistory` in `App.tsx`), not only as a dashboard tab. Character identity there uses full names (`src/lib/liquipedia/chars.ts` maps them to the existing `/public/stock` sprites), not Slippi character IDs. Every panel traces to a listed source, and the Sources panel must keep the CC BY-SA 3.0 attribution — don't add a claim the dataset can't support.
   - **Offline majors only.** Netplay events (Liquipedia's venue column reads "Online") are flagged `online: true` at parse time and filtered out of every total, including the rendered share assets; the view states the exclusion and the count. This is a judgement call, not a data cleanup: 16 events, and it moves Zain from 33 titles to 24, because individual weeks of an online league were counted beside Genesis. Keep the rows flagged rather than deleted so the choice stays auditable.
   - **Winnings are all-Smash and labelled as such.** Liquipedia's "approx. total winnings" covers every Smash title a player entered, and there is no per-game breakdown on the page to quote — only a sum we could compute ourselves from the results tables, which would be our number, not theirs. Don't relabel the column as Melee earnings without doing that work.
7. **Priority of stats** (per owner): kills and win rates — by opponent (connect code), by opponent character, by own character — come first; execution metrics (L-cancel %, tech success, openings/kill, damage/opening, IPM) second. The rolling Actions chart keeps one selected action visible at a time; opponent overlays on all three rolling Execution charts are explicit controls and default off. Sessions exist (a session = games separated by <30-minute gaps — that boundary is load-bearing for the tilt tables; don't change it casually).
   - **The Execution tab reports current form, on one window.** Its KPI strip and all five current-form tables (neutral summary, techs, actions per game, move effectiveness, openings) read `games.slice(-ROLLING_WINDOW)` after the global filters, and each names the count it actually measured rather than the slice length — a window still filling with header previews (decision 10) covers fewer games than it holds. That window is deliberately `ROLLING_WINDOW`, the same number the charts smooth over, which is what makes the **Move trend** chart's final point the very cell the move table shows; the picker's hint says so out loud, so splitting the two constants apart would turn a stated guarantee into a quiet lie. The one thing still on the full filter is `moveImpact`/`actionImpact`, whose median split needs the sample.
8. **File identity and game identity are different things.** `GameRecord.id` (`path|size|mtime`) answers "have I parsed this file?" and stays the cache/`seen`/cloud primary key — it is what makes a rescan cheap. It is *not* a game identity: copying a replay folder changes every path, a Dropbox/Drive/SMB share rewrites mtimes, and re-organizing into per-month subfolders changes both, each producing a second record for a game already held and inflating game counts, hours, and win-rate denominators. `gameKey()` in `dedupe.ts` derives game identity from the replay's own contents instead. Three layers apply it: `dedupeRecords` in App between records and resolve (the correctness guarantee — it covers cache, scan and cloud-pull alike), `pruneDuplicates` at startup (storage), and the `game_key` skip in `pushMissing`/`pullMissing` (stops copies crossing the wire). The survivor is deterministic — real record over tombstone, then lowest id — because those three sources race, and an order-dependent survivor would change a game's React key between loads. **`pruneDuplicates` deliberately leaves the dropped ids in `seen`**: those files still exist on disk, and forgetting them would re-parse the copies and recreate the duplicates on the next scan. It re-reads the packs **inside** its own transaction rather than trusting the array the caller read — rebuilding every pack from a snapshot taken before an `await` is a lost update, and a scan flush or cloud pull landing in that window would be erased while its ids stayed in `seen`: parsed, discarded, and never re-parsed, which is the one combination that loses a game for good.
   - **Never cache a partial read.** A replay read while Slippi is still writing it has no metadata block — slippi-js calls this a "severed incomplete file" — so it has no `playedAt`, and `gameKey()` falls back to the file id in exactly that case. The fragment therefore can never collapse against the finished game: it survives as a dateless phantom inflating every count, and no rescan dislodges it. `parse.ts` rejects these with `IncompleteReplayError` and `pool.ts` writes **no tombstone** for them, because leaving the id out of `seen` is precisely what lets the next scan pick the finished file up. Two cheaper guards sit in front: the pipeline re-stats each file through its handle immediately before reading (the discovery snapshot goes stale mid-scan, and Chrome fails a read whose file changed since), and defers anything modified in the last 10 s. Skips are counted as `ParseProgress.deferred` and surfaced in the UI — they were silent, which is what made "my new games didn't show up" impossible to diagnose.
9. **Sets are always best of three.** Replays carry no set metadata, so `computeSets()` infers it: consecutive games against the same opponent, within a 20-minute gap, run until one side reaches `SET_TARGET_WINS` (2), and the next game against that opponent opens the next set. This replaced a majority-of-the-block rule that deliberately declined to assume a format — it reported five straight games as a single 2–3 "set" when they are two sets. A Bo3 cannot tie, so `GameSet.result` is `"W" | "L"` and no tie branch survives anywhere. An unfinished trailing 1–0 or 1–1 is **not** counted: scoring it by margin is the old rule under another name, and invents a result the games never produced. The consequence to keep in mind is that games which never pair up inside the gap fall outside set stats entirely. The Sets panel and the share card's rival cell both read this one function, so the two can never disagree.

10. **Medium imports have a range-read preview that is never stored; memory-safe imports do not.** From `HEADER_PASS_MIN` (250) through 4,999 pending files, `pool.ts` first runs `parseHeaderFile` over the queue. At 5,000+, the preview and all record streaming are disabled because the temporary React library itself becomes a material crash risk; only progress streams, full records commit to IndexedDB, and the app installs the cache once at completion. A normal replay's UBJSON envelope gives the raw-stream length up front, so the worker reads only the settings prefix (64 KiB, growing to 1 MiB only if needed), the fixed GAME_END command at the raw tail, and the small metadata object after it. No frame is materialized and, critically, the multi-megabyte frame body is not read twice. Unknown/pre-UBJSON layouts fall back to whole-file `parseHeader`. The preview yields identity, stage, characters, mode, duration and (per decision 2) the result — enough for game counts, win rates, matchups, opponents, sessions and the game log — then the full pass follows and replaces those records in place. `scripts/verify-parse.mjs` asserts ranged and whole headers are identical alongside the winner-subset and `gameKey` invariants.
    - **Preview records are transient.** They carry `statsLevel: "header"`; `hasFullStats()` in `types.ts` is the predicate. `pool.ts` writes none of them (nor tombstones — the full pass reaches the same file moments later and is the authority), and `isSyncable` rejects them, which matters because cloud values are keyed by content identity: a pushed preview would replace another device's good value and nothing would ever correct it back. `undefined` is therefore the only `statsLevel` that reaches storage, and every row written before this existed reads as full stats with no migration.
    - **The preview pass is what the user sees first, not just what the parser does first.** The dashboard — or the identity prompt, whose per-code game counts the preview pass has just finished establishing — opens when the *preview* pass ends, and the full pass continues behind it, reporting through the topbar button the way a folder Refresh does. Held back until the whole pipeline resolved, as it was before v0.3.3, the previews are parsed, streamed into React state and never rendered: a second walk of the library bought for nothing, under a progress panel promising win rates first. `startPipeline` in `App.tsx` performs the hand-off on the first frame of the full pass, and everything that follows from a live dashboard mid-run follows from there — `scanBusy` held for the whole run so the re-focus rescan cannot start a second walk of the same folder, the cache merged in so a re-pick over a warm cache does not open on half a library, and the skip tally moved to the topbar, which is where the user now is by the time it is known.
    - **A view whose numbers divide by a game count must be unreachable while previews survive.** `NEEDS_FULL_STATS` in `App.tsx` shuts Execution and Insights on `hasPreviews` — derived from the records, so it clears itself as previews are replaced by id and an incremental refresh never trips it. The per-slice coverage labels of decision 7 are not enough on their own: they can say a table measured 40 of 100 games, but a rolling-average *chart* has nowhere to put that caveat, and it draws a line out of whatever scattered fraction the full pass has reached spread across the x-axis of the whole library. Add a view built on execution metrics and add it to that set. The teams view is deliberately not in it — it is reached through the format filter rather than a tab, and `teamsExecution` already drops previews row by row.
    - **Two places must prefer the full record over its own preview**, because they collide on the *same id*: `preferred()` in `dedupe.ts` (the id tiebreak cannot separate them, so first-wins would keep the preview) and `appendRecords` in `App.tsx` (which merges streamed records by id — it used to skip ids it already had, which would now drop every real record).
    - **Selectors that divide an execution total by a game count must filter on `hasFullStats`.** Sums and ratios-of-sums are safe on their own: a preview contributes 0 to both halves of the L-cancel rate and the neutral share, the `EXEC_METRICS` num/den pairs and the nullable metrics (openings/kill, damage/opening, IPM) are excluded by their existing null guards, and the teams damage matrices are skipped by `accumulate`. What is not safe is any per-game or per-minute average, whose denominator would count games the numerator has no numbers for — `overview`, `byMode`, `byAccount`, `groupRows`, `neutralSummary`, `actionAverages`, `actionImpact`, `lCancelSeries`, `teamsExecution` and `singlesRecords`' damage record all gate for this reason. Game counts, win rates and durations deliberately keep counting every game, since the header supplies all three.

## Design system

Dark GameCube-indigo theme, tokens in `src/index.css` (`--bg #121022`, accent `#8f7ff7`, win `#3fcf8e`, loss `#f0564f`, gold `#e8b54d` = attention, e.g. unsynced games). Fonts: Chakra Petch (display), Inter (body), IBM Plex Mono (data — always tabular numerals for stats). Win-rate coloring goes through `winRateColor()` in `src/lib/format.ts`; don't introduce ad-hoc greens/reds. Chart styling goes through `src/components/chartStyle.ts` (`axisStyle`, `tooltipStyle`, `gridStyle`, `dayTick`); **red is reserved for loss/danger** — comparison series like opponent overlays use `OPP_SERIES_COLOR` (muted, dashed), never red.

The animated bar lists (`.lq-race`, both Liquipedia playbacks) size their transitions off `--lq-step`, which each chart sets from its own frame duration and the selected speed — the durations must never be hard-coded again. They were, and since 2× is the *default* speed a frame lasted 220 ms against a 280 ms row slide and a 500 ms bar growth: rows were permanently mid-flight and a bar was still drawing two frames after the count beside it had moved on. For the same reason the Playbar's caption gets its own full-width row with two lines of height reserved: it names the current frame, so its width changed on every step, and the slider next to it was the `flex: 1` element absorbing the difference — the scrubber grew and shrank by up to 80 px a step, dragging its own thumb sideways. Nothing in that row may be content-sized (hence `min-width` on the Share button, whose label counts through "Rendering 7%…100%").

Categorical series colors (the Liquipedia character charts) come from `CHAR_COLORS` in `src/lib/liquipedia/chars.ts`: a fixed 7-hue order validated for colorblind separation against the `--panel` surface, with everything past it folded into a single `Other` grey — never generate an eighth hue. `CHAR_STACK_ORDER` is that validated adjacency, and the clustered per-edition bars render in it — keep that, since the CVD guarantees were measured on neighbouring pairs. The year explorer sorts by head-count instead, so its hues land in an arbitrary order; that's fine because every row there carries a stock icon and a name, and colour isn't doing the identifying. Ordinal splits (major vs supermajor) use two steps of one hue instead, and pair them with a legend plus a tooltip listing the underlying rows, since the dim step sits under 3:1 on this surface.

## Conventions

- TypeScript strict **plus `noUncheckedIndexedAccess`** — indexing returns `T | undefined`; use the guard-then-`!` pattern already established in `pool.ts`/`parse.ts` rather than weakening types. `npm run build` (tsc + vite) must pass before any push.
- Selectors in `stats.ts` must be single-pass O(n) — libraries can reach 30k+ games.
- **Day/week bucketing is local time** (`localDay` and friends in `stats.ts`) — never `toISOString()` for day keys; date-only strings parse as UTC and shift a day west of Greenwich.
- New aggregate views: respect the global `Filters` and the click-to-filter pattern (clicking a row/cell scopes the dashboard).
- Sample-size honesty: any win-rate display over small n should fade or badge it (see matchup matrix `minGames`).
- Smoke-test selectors against demo data (`generateDemoRecords`) when touching `stats.ts`.
- **Commits are authored as `Studio Pinball <info.studio.pinball@gmail.com>`** — the same address the app publishes as its contact. `.githooks/pre-push` refuses to push anything else. Git will not run a tracked hook until the clone opts in, so a fresh clone needs `git config core.hooksPath .githooks` once; without it the guard is silently absent.

## Deployment

Vercel, deploying `main`. Three things to know before touching config:

- **PWA**: `vite-plugin-pwa` precaches the entire shell — all lazy chunks, fonts, icons — so the app works offline. If you add a new asset *type*, check `globPatterns` in `vite.config.ts` covers it. Registration is **manual** (`injectRegister: null` in `vite.config.ts`): `src/main.tsx` registers the SW itself and polls `registration.update()` hourly so a tab left open picks up new deploys — don't re-enable the plugin's auto-registration, which would silently drop that poll.
- **Build identity**: `__BUILD_ID__` (defined in `vite.config.ts` from the git commit, declared in `src/global.d.ts`) is stamped onto the footer in `App.tsx` as `data-build`. It is no longer printed on the page, but it is still how you verify a deploy actually rolled — `document.querySelector(".site-footer").dataset.build`, or grep the served bundle for the commit. Keep it in the DOM: a deploy you cannot identify is a deploy you cannot debug.
- **Static pages need two settings to work.** `vercel.json` sets `cleanUrls: true` so `dist/about.html` serves at `/about`; Vercel defaults that to `false`, and without it every link and canonical on those pages 404s. `vite.config.ts` needs the matching `navigateFallbackDenylist` (both the bare and `.html` forms), or the service worker answers those navigations from the precached app shell and anyone who has already loaded the site gets the SPA instead of the page. **And vercel.json takes no comments** - the
  schema is `additionalProperties: false`, so a `"//"` key, or any key Vercel does not
  declare, is a hard validation error that fails the deployment before the build
  starts. Nothing local catches it: the file is still valid JSON, so no linter
  complains, and a local build never reads it. Explanations go here instead.
- **CSP** in `vercel.json` allows connections only to self + `*.supabase.co`. Any new network destination must be added there deliberately — a blocked request in production is the symptom.
